# Обучение на архивных прогнозах NOAA GFS

## Контракт

`ml/build_gfs_training_dataset.py` создаёт одну строку на пару «forecast origin × целевой час × турбина». Для origin выбирается последний **полный** выпуск GFS, у которого каждый GRIB-объект и его индекс имеют `Last-Modified <= origin`. Проверка выполняется существующим `backend/weather/gfs.py` и `backend/replay/temporal.py`. Снимки сохраняются в `.cache/weather` и копируются в `data/gfs-training/mvp-2025-08-to-2026-01/snapshots/` с URL, временем доступности, byte range и SHA-256. В набор попадают только реальные полные часовые значения normalized active power из двух CSV; фактические SCADA wind/temperature не становятся признаками.

Временное правило CSV: исходные часы интерпретируются как `Asia/Almaty`, агрегирование — среднее шести корректных 10-минутных измерений. Для используемого диапазона август 2025 — январь 2026 неоднозначного перехода часов нет. Доступность SCADA считается `target_end + 0 h` **только как неподтверждённое допущение** из `ml/config.brev-assumptions.json`; при подтверждённой задержке нужно пересобрать dataset и повторить split/обучение.

MVP использует фиксированное время origin `06:00 UTC`, 48 часов прогноза, даты из `ml/gfs-origins-mvp.txt`. Это разреженная еженедельная выборка, а не все оперативные выпуски. Файл позволяет воспроизвести точные даты; параметры `--start`, `--end`, `--step-days` позволяют расширить период.

Признаки готовятся одной функцией `backend/forecasting/gfs_features.py` в training и serving. `origin_lead_hours` равен 0–47 для первого–последнего целевого часа; `gfs_lead_hours` считается от времени инициализации GFS и при origin 06:00 UTC обычно равен 6–53. Метрики по прогнозному часу используют `origin_lead_hours + 1`, то есть группы 1–6, 7–12, 13–24, 25–36 и 37–48. Погода GFS мгновенная на начало целевого часа; мощность SCADA — среднее за следующий час.

## Воспроизведение

Из корня репозитория на Linux (Python 3.11–3.13):

```bash
python -m venv .venv
.venv/bin/pip install -r ml/requirements-brev.txt -r requirements-weather.txt -r requirements-backend.txt
.venv/bin/python -m ml.build_gfs_training_dataset \
  --start 2025-08-04T06:00:00Z --end 2026-01-27T06:00:00Z \
  --origins-file ml/gfs-origins-mvp.txt \
  --out-dir data/gfs-training/mvp-2025-08-to-2026-01 --workers 4
.venv/bin/python -m ml.train_gfs \
  --dataset-dir data/gfs-training/mvp-2025-08-to-2026-01 \
  --out-dir artifacts/models/gfs-pooled-lgbm-mvp-20260131 \
  --validation-start 2026-01-01T00:00:00Z \
  --final-cutoff 2026-01-30T18:00:00Z \
  --first-required-origin 2026-01-31T06:00:00Z
```

Для повторной сборки уже выбранных 11 origins без сети укажите `--cache-dir data/gfs-training/mvp-2025-08-to-2026-01/snapshots` и новый `--out-dir`, например `/tmp/gfs-rebuild`. При обучении код повторно сверяет SHA-256 каждого сохранённого snapshot и его временной контракт.

Train выбирается по `origin_time < 2026-01-01T00:00Z` **и** `label_available_at <= 2026-01-01T00:00Z`. Таким образом 48-часовые target, пересекающие границу, исключаются из train. Validation использует origins с 1 января до финального cutoff и только labels, доступные до cutoff. Выбор между GFS power curve и pooled LightGBM сделан по общей MAE на идентичных validation-строках; после сравнения LightGBM переобучается на всех допустимых до cutoff строках. Экспортируемая финальная модель не имеет отдельной holdout-метрики: опубликованные validation-метрики относятся к модели до переобучения.

`2026-01-31T06:00Z` — рабочее предположение о первом запуске 31 января; точное время и SCADA latency должны быть подтверждены владельцем процесса. Финальный cutoff `2026-01-30T18:00Z` предшествует ему на 12 часов. Модель обучена ретроспективно сейчас на исторических данных; audit доказывает информационную отсечку, а не фактическое существование артефакта в январе.

Старая оценка MAE `0.030807` относится к модели на фактических SCADA wind/temperature и другому validation-периоду. Она **не** оценивает 24–48-часовой прогноз и не является честным прямым сравнением с GFS MAE. В `metrics_summary.json` новая оценка помечена как archived-GFS retrospective validation; февральская точность не заявляется без февральских labels.

## Фактический результат MVP

Собрано 11/11 выбранных origins (7 train, 4 validation), 11 различных GFS cycles, 1 056 строк (672 train, 384 validation), 0 пропущенных labels для выбранных снимков. Train labels заканчиваются `2025-11-12T06:00Z`, validation labels — `2026-01-28T06:00Z`; обе границы предшествуют соответствующим cutoff. Исторические даты намеренно разрежены: 6 недель августа–сентября, 1 неделя ноября и 4 недели января. Оценка может сильно меняться при расширении выборки и не гарантирует качество на ежедневном графике.

| Кандидат | Validation MAE | RMSE | R² | Turbine 1 MAE | Turbine 2 MAE |
|---|---:|---:|---:|---:|---:|
| GFS power curve | 0,204392 | 0,273903 | 0,450278 | 0,208112 | 0,200673 |
| GFS pooled LightGBM | 0,247199 | 0,297699 | 0,350609 | 0,245364 | 0,249034 |

Power curve выигрывает по заранее установленному правилу минимальной общей MAE. Оба кандидата проверены на одинаковом наборе из 384 ключей `(origin, target, turbine)`; SHA-256 набора ключей записан в `metrics_summary.json`. Детали по группам горизонта и турбинам находятся там же. Оба bundle переобучены на 1 056 строках до финального cutoff, поэтому их итоговые экспортированные версии не имеют независимого holdout score. `gfs-power-curve-mvp-20260131` — рекомендуемый проверенный bundle для выбранного origin schedule; `gfs-pooled-lgbm-mvp-20260131` — экспериментальный, backend предупреждает о проигрыше baseline. На архивном snapshot `2026-02-06T06:00Z` оба дали по 96 конечных прогнозов в `[0,1]`; февральских labels для подсчёта ошибки нет.
