# Autonomous Wind Forecast Operator — архитектура MVP

Статус: архитектурное направление согласовано; реализация ещё не начата. Источник: ТЗ HackAlem AI и полный анализ из issue #1.

## Уточнения после обсуждения

- Автоматический пересчёт при изменении входов — MUST HAVE по ТЗ.
- Обучение численной модели выполняется в NVIDIA Brev; OpenAI остаётся единственным LLM-провайдером. Brev используется как вычислительная среда, без сторонних foundation models.
- Для защиты нужен настоящий запуск OpenAI с tools; offline trace служит отдельным режимом воспроизведения.
- Итог ВЭС зависит от подтверждения нормализации и номиналов; до этого агрегат помечается условным.
- План реализации: [implementation-plan.md](implementation-plan.md). Обучение: [brev-training.md](brev-training.md).


## A. Что обнаружено в предоставленных данных

### 5. Пригодность для hourly forecasting и resampling

**Истории достаточно для табличной модели почасовой мощности. Основные ограничения — пропуски, неизвестная семантика timestamp и отсутствие эксплуатационных статусов.**

Предлагаю:

| Данные | Обработка |
|---|---|
| Нормализованная мощность | Среднее шести 10-минутных средних |
| Ветер SCADA | Почасовое среднее; для исторических признаков также std/min/max |
| Температура SCADA | Почасовое среднее |
| Пропуски | Явная временная сетка и `coverage`; не заменять нулями |
| Target неполного часа | Для MVP исключить из обучения и оценки |
| Длинные разрывы | Не интерполировать |
| Направление ветра NWP | Работать через `u/v` или sin/cos |
| NWP с шагом больше часа | Интерполяция внутри одного допустимого выпуска с фиксацией метода |

Сначала необходимо выяснить, timestamp обозначает **начало или конец 10-минутного интервала**. От этого зависит состав часа и момент доступности измерения.

Средняя мощность и энергия — разные величины:

`E_h = P_rated × mean(p_h) × 1 час`.

Номинальные мощности и способ нормализации не указаны. Поэтому пока прогнозируем **нормализованную мощность**, не выдаём её за МВт или МВт·ч.

Для ВЭС:

`p_farm = (C1 × p1 + C2 × p2) / (C1 + C2)`.

Простое среднее допустимо при равных номинальных мощностях и совместимой нормализации. До подтверждения показываем две турбины отдельно, а агрегат обозначаем как условный.

## B. Предлагаемая архитектура

**Один Python backend, один worker, PostgreSQL и файловое хранилище артефактов. Один frontend.**

Логический процесс:

```text
Scheduler / Replay CLI / API
             ↓
       Immutable Run Context
       as_of + horizon + policy
             ↓
       OpenAI Operator
             ↓ tools
 Weather → Validation → Features → Forecast → Validation
             ↓
     Deterministic publish gate
             ↓
 Forecast storage + audit + dashboard
```

Каждый инструмент получает контекст запуска от backend. Агент не может самостоятельно передвинуть `as_of` или подменить набор данных.

| Решение | Вариант 1 | Вариант 2 | Для хакатона |
|---|---|---|---|
| Workflow | Python state machine | Temporal / Airflow | State machine: меньше инфраструктуры |
| Выполнение задач | PostgreSQL jobs + worker | Redis + Celery | PostgreSQL jobs |
| ML | LightGBM | Нейросеть временных рядов | LightGBM |
| Артефакты | Локальный Docker volume | S3 / MinIO | Volume с интерфейсом хранилища |
| Погодный архив | NOAA GFS GRIB | Open-Meteo Single Runs | GFS как основной кандидат |

API и worker используют один образ и общую бизнес-логику. Не нужны микросервисы, vector database, RAG или отдельная команда LLM-агентов.

## C. Forecasting approach

### 1. Baselines

Нужны минимум два сравнения:

1. **Persistence:** последнее доступное полное часовое значение на весь горизонт. При старых SCADA явно отмечать устаревание; это контрольный baseline.
2. **Weather baseline:** простая регуляризованная зависимость мощности от **архивного прогнозного ветра**, отдельно для турбин.

Дополнительный диагностический baseline — эмпирическая кривая «фактический ветер SCADA → мощность». При подстановке NWP потребуется калибровка: ветер метеомодели и датчика турбины не взаимозаменяемы.

Seasonal persistence можно добавить, но для ветра повторение вчерашнего профиля не стоит считать сильной исходной гипотезой.

### 2. Основная модель MVP

**Одна pooled LightGBM-модель для обеих турбин и всех 48 горизонтов.**

Обучающая строка:

```text
forecast_origin × turbine_id × horizon_hour
```

Target — средняя нормализованная мощность соответствующего будущего часа.

Основные признаки:

- прогнозные компоненты ветра `u/v` на 100 м;
- скорость ветра, вычисленная из `u/v`;
- ветер на 10 м, если доступен;
- прогнозная температура на 2 м;
- `turbine_id`;
- горизонт относительно `as_of`;
- lead time относительно инициализации NWP;
- возраст погодного выпуска;
- час суток и сезонные sin/cos-признаки;
- изменения прогнозного ветра между соседними часами **того же выпуска**.

Высота 100 м — кандидат, а не подтверждённая высота ступицы. При получении паспортов уточняем.

**Базовая модель должна быть weather-only.** Это соответствует фактически доступным данным: весь февраль свежих SCADA нет.

SHOULD HAVE — дополнительная модель или корректирующая ветка со свежими SCADA:

- последние завершённые часы мощности, ветра и температуры;
- backward-looking окна 3/6/24/72 часа;
- возраст последнего измерения;
- доступность и заполненность истории;
- недавняя ошибка предыдущих прогнозов, только после поступления факта.

При устаревших данных эта ветка отключается. Порог устаревания фиксируем по валидации до февраля.

### 3. Какие признаки доступны без утечки

| Признак | Допустимость |
|---|---|
| NWP на будущий час из ранее опубликованного выпуска | Да |
| Календарь будущего часа | Да |
| Исторические SCADA, поступившие до `as_of` | Да |
| Будущий фактический ветер / температура | Нет |
| Rolling mean, рассчитанный вокруг будущего target | Нет |
| Нормализация или imputation, обученные на всём датасете | Нет |
| Остановка турбины, известная только постфактум | Нет |
| Разница двух NWP-выпусков, оба доступны до `as_of` | Да |

Особенно опасен признак `power(target_time − 24h)`: для горизонта +48 часов это значение находится **в будущем относительно запуска**. Лаги привязываем к origin либо проверяем доступность каждого значения.

### 4. Production-путь

Начальная production-модель может остаться LightGBM. Следующие улучшения определяются ошибками:

- калибровка локального ветра и различий турбин;
- эксплуатационные статусы и плановые ограничения;
- ансамбль погодных прогнозов;
- вероятностные прогнозы;
- мониторинг drift и контролируемое переобучение.

Не начинал бы с LSTM/Transformer: здесь сначала нужно решить качество погодных входов и временную корректность обучения.

### 5. Метрики

Предлагаю пять:

| Метрика | Назначение |
|---|---|
| MAE нормализованной мощности | Основная интерпретируемая ошибка |
| RMSE | Штраф за крупные промахи |
| Mean bias: mean(prediction − actual) | Систематическое завышение/занижение |
| Skill относительно baseline: `1 − MAE_model / MAE_baseline` | Объективная польза модели |
| Interval score для 80%-го интервала | Баланс ширины и промахов интервала |

Для MAE в диапазоне мощности `[0;1]` значение `0,08` означает 8 процентных пунктов нормализованной мощности.

Отчёт — отдельно по турбинам, ВЭС, горизонтам 1–6 / 7–24 / 25–48 часов. Для интервалов дополнительно показываем фактическое покрытие.

MAPE не рекомендую: в данных много почти нулевой мощности. Все модели сравниваются на одинаковой маске валидных target; пропущенные прогнозы учитываются отдельно, чтобы модель не улучшала метрику отказами.

## D. Agentic AI architecture

### 1. Роль OpenAI

Предложенную схему стоит изменить: **если LLM включается только после готового прогноза, он почти не управляет процессом**.

Предлагаю одного OpenAI Operator, который вызывает инструменты и выбирает разрешённые действия:

- получить пригодный погодный выпуск;
- при недоступности проверить предыдущий допустимый выпуск;
- выбрать основную или разрешённую резервную модель;
- запросить дополнительную диагностику;
- опубликовать результат с предупреждениями;
- остановить публикацию при критической проблеме;
- запросить новый запуск после изменения входов.

Интеграция — Responses API с function tools и строгими JSON-схемами. Сами функции выполняет приложение; LLM формирует вызовы. Это соответствует [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/function-calling).

### 2. Инструменты

Не нужно раскрывать агенту каждую внутреннюю функцию.

| Tool | Результат |
|---|---|
| `get_run_context()` | Зафиксированные параметры и доступные действия |
| `get_weather_forecast()` | ID допустимого погодного snapshot |
| `validate_inputs()` | Проверки погоды, SCADA и времени |
| `run_forecast(model_id)` | ID численного результата |
| `validate_forecast()` | Проверки, интервалы, предупреждения |
| `publish_forecast()` | Публикация после обязательного gate |
| `request_recalculation(reason)` | Новый связанный запуск |

`load_scada_history`, `prepare_features` и расчёт интервалов остаются внутренними детерминированными функциями.

### 3. Что LLM не решает

Код отвечает за:

- доступность данных во времени;
- resampling и признаки;
- обучение и inference;
- физические ограничения;
- метрики и интервалы;
- retries сетевых запросов;
- идемпотентность и запись в БД;
- окончательный запрет публикации при утечке.

Агент не может отменить critical validation failure, исправить числа текстом или объявить `leakage=NONE`.

Для наглядной демонстрации агентности используем сценарий отказа источника: агент получает диагностическое сообщение, выбирает допустимый предыдущий выпуск и публикует прогноз с предупреждением. Искусственный сбой в демо обозначается явно.

Ограничения: максимальное число tool calls, таймаут, ограниченный список моделей и источников. При недоступности OpenAI допускается отдельно обозначенный deterministic fallback; это не следует выдавать за работающий AI-agent.

## E. Replay/backtesting architecture

### 1. Источник архивных прогнозов

**Основной кандидат — NOAA GFS из публичного S3-архива. Существование конкретного февральского выпуска проверено непосредственно.**

Проверенный объект:

```text
gfs.20260205/18/atmos/gfs.t18z.pgrb2.0p25.f048
```

Получены:

- инициализация: **05.02.2026 18:00 UTC**;
- lead time: **48 часов**;
- `LastModified` GRIB: **05.02.2026 21:59:37 UTC**;
- `LastModified` индекса: **05.02.2026 22:00:09 UTC**;
- индекс содержит `UGRD/VGRD` на 100 м и другие необходимые поля.

Официальный реестр подтверждает публичный bucket и доступ без AWS-аккаунта: [NOAA GFS на AWS](https://registry.opendata.aws/noaa-gfs-bdp-pds/).

**Это проверка одного файла и индекса, не подтверждение полноты всего февраля или готового извлечения значений по координатам.**

План адаптера:

1. Найти допустимый цикл.
2. Получить `.idx`.
3. Скачать HTTP Range-запросами только необходимые GRIB-сообщения.
4. Извлечь значения ближайших ячеек / билинейную интерполяцию.
5. Сохранить небольшой immutable snapshot для ВЭС.

Полный проверенный файл занимает около 544 МБ. Скачивать все переменные для каждого часа нерационально.

Для горизонта 48 часов от `as_of` нужен NWP, покрывающий **возраст выпуска + 48 часов**, а не просто `f048`.

### 2. Альтернатива: Open-Meteo

Open-Meteo Single Runs API поддерживает выбор конкретного выпуска через `run`. Документация указывает архив большинства моделей только с 02.04.2026; исключение — ECMWF IFS с марта 2024 года. Она также отдельно предупреждает, что `run` — время инициализации, а доступность наступает позже. В описании раннего ECMWF-архива присутствует формулировка *hindcasts*: происхождение нужных февральских выпусков следует дополнительно проверить. [Single Runs API](https://open-meteo.com/en/docs/single-runs-api)

Trade-off:

- Open-Meteo проще интегрировать;
- GFS GRIB требует больше обработки, но даёт явно идентифицируемые оперативные файлы и метаданные объектов.

**Для хакатона предлагаю GFS.** Open-Meteo оставляем альтернативой после проверки provenance. Historical Weather, ERA5 и сшитые исторические ряды не подставляем вместо доступного тогда прогноза.

### 3. Временной контракт

Для каждого источника различать:

| Поле | Значение |
|---|---|
| `event_time` / `valid_time` | К какому времени относится значение |
| `init_time` | Время инициализации погодной модели |
| `available_at` | Когда этот объект стал доступен |
| `ingested_at` | Когда наша система реально его скачала |
| `as_of` | Граница информации симулируемого запуска |

Для replay загрузка архива сегодня допустима: сегодняшний `ingested_at` не равен историческому `available_at`.

Но историческую доступность нужно подтверждать метаданными или обозначенной политикой. S3 `LastModified` — свидетельство доступности этой версии объекта, а не универсальная гарантия первоначального выпуска.

Если доступность только оценена по расписанию:

```text
availability_basis = assumed_schedule
```

Тогда статус должен отражать допущение, а не безусловное доказательство отсутствия утечки.

### 4. Проверки одного запуска

До inference:

- все SCADA-интервалы завершились и стали доступны не позже `as_of`;
- все используемые погодные объекты доступны не позже `as_of`;
- модель обучена на target, доступных до разрешённого cutoff;
- preprocessing и калибровка подчиняются тому же cutoff;
- snapshot покрывает каждый прогнозируемый час;
- признаки имеют прослеживаемые источники.

В историческом исследовании модель физически обучается сегодня. Поэтому храним отдельно реальное `trained_at` и симулируемый `training_cutoff`; не притворяемся, что артефакт существовал в январе.

### 5. Как проводить февральский replay

**Основной режим с текущими файлами — фиксированная модель и обновляющаяся архивная погода.**

1. Разработка и подбор параметров — на временных разбиениях до февраля.
2. Финальные настройки фиксируются до просмотра февральских target.
3. Воспроизводится запуск 31 января и последующие ежедневные запуски в согласованное время.
4. Для каждого origin выбирается свой доступный погодный выпуск.
5. SCADA остаются ограничены фактически предоставленной историей.
6. Прогнозы и audit сохраняются без перезаписи.
7. При получении февральского факта отдельный evaluator считает метрики.

Если организаторы разрешат последовательное открытие февральских SCADA, это будет **второй явно обозначенный режим**. Нельзя смешивать его с режимом фиксированного входного датасета.

Для обучения и проверки использовать rolling-origin splits. В train не должны попадать примеры, чьи будущие target пересекают cutoff; для 48-часовых примеров нужен соответствующий purge на границе.

Ранний replay 31 января также требует модели, обученной только на доступных к его времени данных. Нельзя использовать весь день 31 января для запуска в его начале.

### 6. Часовой пояс и горизонт

Timezone CSV неизвестен. Храним UTC, но преобразуем исходные timestamp только после уточнения. Нельзя механически применять текущий UTC-offset ко всей истории с 2023 года.

CLI должен принимать timestamp с offset либо требовать явно настроенный timezone:

```text
python replay.py --as-of "2026-02-06T00:00:00+05:00" --horizon 48
```

При таком offset это **05.02.2026 19:00 UTC**. Проверенный GFS-цикл 18 UTC ещё не опубликован и недопустим.

Для origin на границе часа предлагаем 48 интервалов:

```text
[as_of, as_of + 1h), …, [as_of + 47h, as_of + 48h)
```

В API сохраняем `target_start` и `target_end`, чтобы избежать сдвига на час.

### 7. Честная карточка Replay

Для 6 февраля при текущих данных:

```text
Forecast as of:                  06 Feb 2026 00:00 [timezone]
Weather initialization:         [выбранный цикл]
Weather available at:           [подтверждённое время / допущение]
Latest supplied SCADA:          31 Jan 2026 23:50 [timezone]
Forecast horizon:               48h
SCADA status:                   stale
Temporal validation:            PASS / FAIL / ASSUMPTIONS
```

**`Future data leakage: NONE` показываем только при выполненных проверках и явно определённых предпосылках доступности.**

## F. Backend/API

### 1. Стек и endpoints

Предлагаемый стек: FastAPI, Pydantic, PostgreSQL, pandas/NumPy, LightGBM; ecCodes для GRIB. Один worker выполняет длительные задачи.

| Endpoint | Назначение |
|---|---|
| `POST /forecast-runs` | Создать live/replay run |
| `GET /forecast-runs/{id}` | Состояние и параметры |
| `GET /forecast-runs/{id}/forecast` | Почасовые значения |
| `GET /forecast-runs/{id}/audit` | Проверки и provenance |
| `GET /forecast-runs/{id}/events` | Tool calls и workflow |
| `POST /forecast-runs/{id}/recalculate` | Создать связанную ревизию |
| `POST /backtests` | Запустить диапазон origin |
| `GET /backtests/{id}` | Метрики и покрытие |
| `GET /health` | Готовность системы |

Запуск возвращает `202 + run_id`. Для MVP достаточно polling.

### 2. Хранение

PostgreSQL:

- `forecast_runs`;
- `forecast_points`;
- `weather_snapshots`;
- `model_versions`;
- `run_events`;
- `validation_results`;
- `jobs`.

Файлы / Parquet:

- исходные CSV;
- погодные snapshots;
- обучающие выборки;
- модели;
- экспорт прогнозов и audit.

Обязательные поля audit:

- `as_of`, реальное время выполнения, horizon, timezone policy;
- погодный provider/model/cycle;
- `available_at` и основание его определения;
- последний SCADA timestamp и cutoff;
- модель, training cutoff, feature schema;
- hashes исходных данных, погоды и модели;
- версия кода и конфигурации;
- результаты deterministic validation;
- действия агента, версия prompt и OpenAI model ID;
- предупреждения и интервалы;
- `parent_run_id`, причина пересчёта.

Новый расчёт создаёт новый run. Старый прогноз не перезаписывается. Идемпотентность определяется контекстом, версиями и hashes входов.

### 3. Validation и confidence

**Входные проверки:**

- schema, типы, уникальность;
- единицы, timezone, покрытие;
- возраст SCADA и NWP;
- NaN, физически невозможные значения;
- застывшие датчики и необычные сочетания;
- временная допустимость источников.

**Выходные проверки:**

- ровно 24/48 ожидаемых интервала на турбину;
- конечные значения;
- физические границы после подтверждения нормализации;
- правильный порядок квантилей;
- согласованность агрегата;
- резкие изменения и расхождение с baseline как warnings;
- отсутствие запрещённых источников.

Не ограничиваться clipping: сохранять долю и величину исправлений, а крупные нарушения блокировать.

**Confidence:** не придуманное агентом число «93%». Показывать:

- интервал P10–P90;
- его фактическое покрытие на предфевральской валидации;
- свежесть и полноту входов;
- выход признаков за обучающий диапазон.

Для MVP интервалы можно получить из ошибок rolling backtest по группам горизонта. Для ВЭС калибровать ошибки агрегата отдельно: складывать квантили двух зависимых турбин некорректно.

### 4. Пересчёт

Триггеры — новый weather snapshot, новые разрешённые SCADA, исправление источника или ручной запрос.

Worker проверяет, изменился ли hash входов, и создаёт связанную ревизию. Повторный расчёт с теми же данными бессмысленен. В replay новые входы появляются по симулируемым событиям доступности.

## G. Frontend

**React + TypeScript + Vite, одна основная страница.**

Четыре области:

1. **Replay controls:** дата, timezone, горизонт, запуск.
2. **Forecast:** две турбины, агрегат при определённой нормализации, интервалы.
3. **Provenance:** `as_of`, weather init/availability, SCADA cutoff, модель.
4. **Agent timeline:** инструменты, решения, предупреждения и пересчёты.

Отдельная вкладка Backtest — метрики по горизонтам и покрытие.

Фактические будущие значения можно показывать только в явно обозначенном режиме оценки, из отдельного evaluator-источника. Их нельзя передавать агенту или forecasting engine.

Пока нет февральского ground truth, интерфейс показывает **«Фактические данные для оценки не предоставлены»**.

## J. Risks

| Риск | Что проверить первым |
|---|---|
| Неизвестный timezone и смысл timestamp | Уточнить у организаторов до совмещения с NWP |
| Неизвестная нормализация мощности | Узнать формулу, номиналы и единицы ожидаемого submission |
| Нет февральских target | Уточнить доступ к факту и формат оценки |
| Неясно, разрешены ли новые SCADA в феврале | Зафиксировать режим replay |
| Архив найден только точечно | Проверить все нужные lead times, дни февраля и обучающие периоды |
| Публикация позже инициализации | Проверять доступность каждого используемого объекта |
| GRIB extraction занимает слишком много времени | Измерить один полный 48-часовой запуск до UI |
| Ветер NWP плохо описывает локальный ветер | Сравнить NWP с SCADA на предфевральском периоде |
| Низкая мощность при сильном ветре | Сохранить случаи; запросить статусы, не удалять как выбросы |
| Утечка через обучение и калибровку | Проверять cutoffs всех артефактов, не только погоды |
| Агент только комментирует результат | Показать реальную разрешённую ветку восстановления |
| Результат требует внешних сервисов для демонстрации | Подготовить offline fixture и audit |

**До основной разработки нужно закрыть три условия:**

1. Однозначно определить время и target.
2. Извлечь погодные значения для одного настоящего февральского replay с доказуемо допустимым выпуском.
3. Подтвердить, что архив можно собрать для обучения и всего тестового периода за доступное время.

Февральский replay без февральских target — это проверка воспроизводимого процесса, **не доказательство точности прогноза**.

## K. Implementation order

1. **Зафиксировать контракт с организаторами.**  
   Timezone, начало/конец интервала, нормализация, номиналы, график origin, доступность февральских SCADA и формат submission.

2. **Сделать weather feasibility spike.**  
   Один origin → допустимый GFS-цикл → все необходимые часы → значения для ВЭС → provenance. Затем проверить покрытие февраля и обучающего периода.

3. **Подготовить hourly dataset.**  
   Сетка, coverage, маски target, отчёт о пропусках. Сохранить исходные данные неизменными.

4. **Построить минимальный Replay Engine и temporal tests.**  
   Ещё до агента: отбор SCADA/NWP по `as_of`, immutable snapshots, audit.

5. **Реализовать baselines и rolling evaluation до февраля.**  
   Получить первые реальные метрики и время выполнения.

6. **Обучить LightGBM.**  
   Сравнить на тех же origin и target; зафиксировать модель и калибровку.

7. **Довести CLI до полного результата.**  
   Один вызов создаёт прогноз, audit и понятный статус. Проверить повторяемость offline.

8. **Подключить OpenAI Operator.**  
   Строгие tools, ограничения действий, trace; показать нормальный запуск и восстановление после сбоя.

9. **Добавить API, worker и dashboard.**  
   UI читает уже работающие результаты и provenance.

10. **Выполнить февральский replay и упаковать демонстрацию.**  
    Экспортировать прогнозы, проверить 48-часовые горизонты на границах месяца, отделить отсутствующие факты от ошибок системы.

11. **Проверить запуск с чистого окружения.**  
    Docker Compose, offline fixture, инструкция с OpenAI key, версии, checksums, тесты против утечки.

После согласования контрактов команда может параллельно вести weather/replay, ML/evaluation и API/UI. **Общая точка интеграции — один `ForecastRun` с фиксированным `as_of`, ссылками на артефакты и audit.**

Архитектурное направление согласовано. Неопределённости по данным фиксируются как обязательные входные условия в плане; готовность реализации не заявляется.
